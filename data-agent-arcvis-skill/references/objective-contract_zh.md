# objective 文件契约规范

本分册规定 objectives/ 目标文件的完整格式：文件头部的 YAML frontmatter 契约（门禁、依赖指标、产出物声明）与正文段落结构。

objectives/ 目录存放逐分析目标的执行手册：每个分析目标一个 Markdown 文件，回答「下次做这个目标该怎么做、产物长什么样才算合格」。目标文件做的是流程沉淀，不是重新分析数据。文件命名规则见 references/file-structure_zh.md。

## 文件总体结构

每个 objective 文件由两部分组成，顺序固定：

1. **YAML frontmatter**：文件最顶部由成对 `---` 行包裹的合法 YAML，声明门禁（gates）、依赖指标（metrics_deps）、产出物（deliverables）与前置依赖（depends_on）等机器契约；
2. **正文**：纯散文的 Markdown 执行手册，段落结构见下文「正文段落结构」。

frontmatter 是唯一的门禁与依赖指标声明位置：**正文中禁止再写「## 门禁」「## 依赖指标」节**。

## frontmatter 契约（schema v1）

### 完整示例

```yaml
---
contract_version: 1
depends_on: [1]
gates:
  - id: G1
    type: table
    title: 达成率数值表
    severity: blocking
    check: |-
      输出落盘为 达成率明细.csv，包含 12 个月份行、3 个固定列（月份 / 报告数值 / 取数口径），
      列名与 deliverables 声明一致。空值显示为 "N/A"，禁止显示 0。
      本表数值口径以 [METRIC-003] 为准。
  - id: G2
    type: conclusion
    title: 达标判定结论
    check: |-
      对每个战区给出「达标 / 未达标」二值判定，判定基准为达成率 >= 1.0（口径见 [METRIC-003]、[METRIC-016]）。
      结论必须引用具体数值，禁止只写定性描述。
  - id: G3
    type: constraint
    severity: warning
    title: 禁止对率求平均
    check: |-
      换粒度时先聚合分子、分母再相除，禁止对达成率本身 SUM/AVG。
      仅当本目标涉及跨粒度汇总时适用。
metrics_deps:
  - id: METRIC-003
    usage: |-
      判断月度达成健康度，达成率列与状态判定用
  - id: METRIC-016
    usage: |-
      战区粒度实销达成率计算
deliverables:
  - file: 达成率明细.csv
    columns: [月份, 报告数值, 取数口径]
---
```

### 顶层字段

| 字段 | 必填 | 说明 |
|---|---|---|
| contract_version | 必填 | 固定填 `1` |
| gates | 必填 | 门禁清单，至少一条 |
| metrics_deps | 必填 | 依赖指标清单；本目标不依赖任何指标时填空列表 `[]` |
| deliverables | 可选 | 落盘产物的文件名与列名声明 |
| depends_on | 可选 | 前置 objective 的 order 数字列表（如 `depends_on: [1]`），平台结构化消费；无依赖写 `[]` 或整键省略（旧包无此字段不受影响），写作指引见下方「depends_on 写作指引」 |

### depends_on 写作指引

`depends_on` 声明本目标的前置目标（执行顺序上必须先完成的 objective），产出规则三条：

1. **有依赖照抄**：源头计划（样例任务的 plan）已声明依赖时，照抄该列表——不增、不减、不改序号；
2. **无依赖自行判断**：源头无依赖声明时，根据分析逻辑判断合理前置，依据仅限两类：
   数据产物流转（本目标读取前置目标落盘的文件）、概念定义先后（如基准月定义、共享口径由前置目标确立）；
3. **禁止编造**：无真实前置就留空，禁止为凑数编造链式依赖（如机械地让每个目标依赖前一个）。

约束：只引用包内存在的其他目标的 order，禁止自引用，全包不得成环（校验器以 WARN 提醒）。

### gates 条目字段（标准五字段）

标准写法只用核心五字段：id / type / title / check / severity，**尽量不要写其他字段**。

#### 核心五字段（前四项建议必填，severity 可选）

| 字段 | 档位 | 说明 |
|---|---|---|
| id | 建议必填 | 格式 `G` + 数字（完整匹配 `^G\d+$`），同一文件内建议不重复；渲染时的 G 编号由平台按序分配，id 主要服务于报告联动溯源与人工阅读 |
| type | 建议必填 | 建议取 `table` / `conclusion` / `constraint`；`chart` 为保留值，禁止手工填写（见下方「type 取值规则」）；缺失或取值非法时该条落入「其他门禁」分区 |
| title | 建议必填 | 门禁标题，一句话概括校验对象 |
| check | 建议必填 | 校验说明自由文本，**强烈建议使用 `\|-` 块标量写法**（见下方「块标量写法」） |
| severity | 可选 | 取 `blocking`（不达标即不合格）或 `warning`（提示级），缺省视为 `blocking` |

#### 不要写五字段之外的键

- 格式、展示、排序、适用条件等一切要求**一律写进 check 的 `|-` 块标量文本**，不要发明自定义键（如 verify / metrics / when / ext 或任意键）承载它们；
- 如实说明：多余字段平台**不会拒收**，会随原始 YAML 整块透传给大模型（见下方「平台处理承诺」），但工程不解析、没有任何结构化消费——写了没有额外收益，徒增噪音；
- validate_skill.py 对五字段之外的键输出 WARN 提醒（不判 FAIL）；
- 指标依赖统一声明在顶层 `metrics_deps`，不要写 `gates[].metrics`（若写了，合法 `METRIC-NNN` 项仍参与指标引用交叉校验，但这只是存量兼容，不是标准写法）；
- 唯一带结构化消费的例外是报告联动场景的 `ext.report_metrics`（参与 R1 校验，见 references/report-structure_zh.md）；无报告联动需求时不要写 ext。

### 平台处理承诺（宽容透传）

- 门禁块一经识别（frontmatter 为合法 YAML 且含 `contract_version`，见下方「frontmatter 硬约束」），每条 gate 的**原始 YAML 整块透传给大模型**，五字段之外的多余字段大模型也全量可见，不会被平台丢弃；
- 个别条目不规范（缺 id/title/check、type 非法等）**不会导致门禁丢失**，其余条目不受牵连；
- type 缺失或取值非法的条目仅落入「其他门禁」分区，整块照常透传，但不参与图表装配、结论/产物块提取等按 type 过滤的机制。

#### type 取值规则

- `table`（表格产物交付）：文件/表格的行数、列名、排序等硬校验；
- `conclusion`（结论交付）：必答问题、判定标准、结论格式；
- `constraint`（过程约束）：执行方式约束，宜少而精；
- `chart`（图表产物交付）：**保留给自动生成流程写入，人工编写 objective 时禁止填写**——图表的规格与画图思路写入正文「## 图表方法论」节。

#### check 编写要求

- 措辞必须精确到可机器校验，禁止「已输出」「已生成」「合理」「适当」等模糊措辞；
- 其中的表头列名、文件名必须与 deliverables 声明及业务约束一致；
- 文本产物有业务方指定模板时写「以 report_template.md 对应章节为准」。

### metrics_deps 条目字段

| 字段 | 必填 | 说明 |
|---|---|---|
| id | 必填 | 指标 ID，完整匹配 `^METRIC-\d{3}$`（NNN 三位数字），必须与 metrics/ 目录下的文件名一致，不遗漏、不编造 |
| usage | 必填 | 一句话说明本目标用这个指标做什么，**建议使用 `\|-` 块标量写法** |

只用 ID 引用，禁止在 usage 中重复定义指标口径——指标手册是唯一权威定义源。

### deliverables 条目字段

| 字段 | 必填 | 说明 |
|---|---|---|
| file | 必填 | 固定产物文件名 |
| columns | 可选 | 固定列名清单，与正文「## 产出物」节描述一致 |

**被报告模板直读消费的 deliverable（直读契约）**：该文件将被模板 `$read` 指令引用时，columns 从可选升级为必填，且 check 必须锁定**四锁**格式契约——

1. 文件名固定（禁止含日期、批次、序号等可变成分）；
2. 列名与顺序固定（列名即直读契约，改列名等于改契约）；
3. 行粒度与表形态明确（一行 = 什么、宽表 / 长表、行数预期）；
4. 文件格式明确（csv：UTF-8 首行表头；xlsx：多 sheet 时写明 sheet 名），行数 ≤ 1000。

直读的稳定性完全等于源文件格式的稳定性：后续迭代改动任一锁，必须同步模板侧（column_map / schema / fill_guide），联动记号与校验规则见 references/report-structure_zh.md 的 R4 与 references/web-report-template_zh.md 第五节。

### 块标量写法（强烈建议）

- `check`、`usage` 等自由文本字段**建议一律使用 `|-` 块标量写法**：字段名后接 ` |-`，内容另起行并缩进；
- 避免把含冒号、引号、`#`、`%` 等特殊符号的长文本写成单行流式标量——这类写法极易产生非法 YAML，而「整体必须是合法 YAML」是硬约束红线；
- 块标量内部可安全使用任意标点与多行文本，无需转义；
- 单行短枚举（如 `depends_on: [1]`、`columns: [月份, 报告数值]`）可用流式写法。

### frontmatter 硬约束（红线仅两条）

1. **整体必须是合法 YAML**：以文件第一行的 `---` 开始、以成对的 `---` 行结束，禁止用 Markdown 代码围栏（```）包裹——写坏任意一处都会导致整个 frontmatter 无法解析；
2. **必须含 `contract_version`**（固定填 `1`）——这是平台识别门禁契约块的前提。

触碰红线时门禁块无法被识别，整体回落旧正文解析；除此之外的原有红线一律降为建议：

- gates 的 id 在同一文件内建议不重复（重复不丢门禁，validate_skill.py 以 WARN 提示）；
- 每个 `METRIC-NNN` 引用（gates[].metrics 与 metrics_deps[].id）应在 metrics/ 目录有同名 `.yaml` 文件——此条不影响门禁识别，但指标手册闭合是工程要求，validate_skill.py 对缺失文件仍判 FAIL；
- gates 缺失或为空同样不影响块识别，但空契约无意义，validate_skill.py 仍判 FAIL。

## 正文段落结构（顺序固定，段落齐全）

frontmatter 之后的正文按以下顺序编排：

1. `# 目标：{目标名}`：与文件名中的名称部分一致。
2. `## 分析思路`：这个目标怎么拆解、按什么逻辑分析；时间范围/筛选条件/排序规则必须与业务约束一致；时间窗口表述必须自洽——禁止写与实际范围矛盾的「近 N 个月」计数，拿不准就直接描述范围（如「去年 1-12 月 + 今年 1 月至基准月」）。
3. `## 数值清单`：产物中每个展示数值的取数口径表（格式见下）。
4. `## 用到的表`：逐行 `- {表名}`；只用表名引用，禁止重复描述表结构。
5. `## 产出物`：本目标交付产物清单（格式见下）。
6. `## 图表方法论`：图表产物的规格与画图思路（格式见下）；无图表时保留本节标题并注明不适用。

指标手册是唯一权威定义源：正文全程只用 `[METRIC-NNN]` ID 引用指标，禁止重复定义指标口径。

### 数值清单格式

用 Markdown 表格逐个数值给出取数口径，表头三列固定：

| 报告数值 | 取数口径（过滤 → 聚合 → 公式） | 依赖指标 |
|---|---|---|
| {数值/列名} | {口径描述} | {METRIC-ID 或指标名，无则 —} |

必须覆盖本目标产物中出现的每个展示数值，做到报告里每个数字都能在本表找到口径出处。涉及率指标时，分母口径必须与指标手册的定义一致。

### 产出物格式

逐个列出本目标的交付产物，骨架：

- **{产物文件名或表格名}**：{行数/粒度 × 逐列列名清单，排序与格式约定}
- **{图表/结论类产物}**：{主题、数量、格式要点}

落盘文件必须写明固定文件名与固定列名，并与 frontmatter 的 deliverables 声明一致；纯报告类目标可为报告章节的表格/图表产物描述。

### 图表方法论节写法

每张图一段「### 图表门禁：{图表标题}」，段内两部分：

- **图表规格**：图表类型、图表标题、X 轴（字段/标签/刻度规则）、Y 轴（字段/标签/单位）、数据系列（名称/数据来源/颜色/类型）、辅助元素（网格线/图例/数据标签/警戒线/布局）；
- **画图思路**：这张图想说明什么、关键设计决策是什么。
